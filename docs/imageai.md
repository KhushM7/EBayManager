# Photo AI: background removal, spot removal, upscale

K's decision (2026-11-13): the photo editor's AI tools run on three open models in K's own container, not a paid
API. They're billed only while one of them runs, never when idle. The photo rule they serve is
[add-listing.md](add-listing.md), decision 4: clean up around the item, never change the item.

| Tool | Model | Notes |
| --- | --- | --- |
| Remove background | IS-Net general use (rembg's model and method) | The item cut out with soft edges; the editor puts it on white |
| Spot removal | LaMa (Large Mask inpainting), ONNX | Fills a painted area from the texture around it; for clutter around the item only |
| Upscale | Real-ESRGAN realesr-general-x4v3, ONNX | Sharper detail and more pixels, up to 2400 px on the long side; denoise strength 0.2, 0.5 or 0.8 |

## How it fits together

```
phone (editor)  --POST /api/photo-ai/{op}, session cookie-->  Function App (src/imageai.ts)
                                                                 checks the photo, strips metadata,
                                                                 adds X-ImageAI-Key, waits up to 180 s
Function App    --POST {IMAGEAI_URL}/v1/{op}-------------->  Container App (imageai/app.py)
                                                                 0 replicas when idle; starts on demand,
                                                                 runs the model, returns the photo
```

- **Container** (`imageai/`): Python 3.12 slim, FastAPI, onnxruntime CPU, Pillow. No PyTorch at run time. Models are baked into the image at build time, each checked against a pinned SHA-256, and loaded lazily on first use. It's about 1.2 GB unpacked. Details and licences: [imageai/README.md](../imageai/README.md).
- **Image registry**: GitHub Container Registry, public (`ghcr.io/khushm7/ebaymanager-imageai`). It's free and needs no registry password in Azure. An Azure Container Registry was ruled out because even Basic bills every day.
- **Hosting** (`infra/modules/imageai.bicep`): an Azure Container Apps environment on the Consumption plan, with no Log Analytics workspace (that would bill ingestion). One app at 2 vCPU and 4 GiB, scaling from **0 to 1 replica** on HTTP and back to zero **2 minutes** after the last request.
- **Secrets**: `IMAGEAI_KEY` is generated by `scripts/make-keys.mjs` and uploaded with `scripts/azure-secrets.mjs`. The Function App reads it from the environment's Key Vault. The container gets it as its own encrypted Container Apps secret, passed in by `scripts/azure-infra.mjs` straight from the vars file (never printed): Azure now creates Container Apps environments in "express" mode, which can't read Key Vault secrets (found on the first production deploy, 2026-11-13). The container's address is written by the infrastructure into the same vault as `IMAGEAI-URL`, which the Function App reads like its other secrets.
- **Health**: calls are recorded as the service `imageai` (`src/services.ts`). A rejected key alerts at once; repeated failures alert with an Inbox to-do. Settings → Usage and APIs shows "Photo AI" once it's set up.

## Costs

Azure Container Apps (Consumption) bills per second while a replica exists, with a **free grant every month of
180,000 vCPU-seconds, 360,000 GiB-seconds and 2 million requests** per subscription. With 0 replicas there is
nothing to bill, so **idle costs £0**.

Each burst of edits starts the container once and keeps it alive while editing, plus 2 minutes before it scales back to zero:

| | Seconds | vCPU-s (2 vCPU) | GiB-s (4 GiB) |
| --- | --- | --- | --- |
| Start (pull the image if needed, load) | ~30–90 | ~120 | ~240 |
| One edit (measured at 2 vCPU: cut-out 2.5 s, spot removal 7 s, upscale 16 s) | 3–16 | ~6–32 | ~12–64 |
| Wind-down before scaling to zero | 120 | ~240 at most (idle rate) | ~480 |

That's under 400 vCPU-s and 800 GiB-s per session, so the free grant covers about **450 editing sessions a
month**. K's use is a few listings a week. Beyond the grant, a session costs about 1p at Azure's published
per-second rates (check the [pricing page](https://azure.microsoft.com/en-gb/pricing/details/container-apps/);
the exact rates weren't confirmed when this was written). Nothing else in this setup bills: the environment is
free, there's no registry and no log workspace. The $5 budget alert in `infra/main.bicep` still covers the
subscription.

The first edit after a quiet spell waits for the container to start (30–90 s). The editor shows a progress
state, and the app waits up to 180 s before giving up with "try again in a minute".

## Deploying (K)

Nothing here runs or costs anything until step 4.

1. **Build the image.** Merge the branch to `main`. The `imageai` GitHub Actions workflow builds and publishes the image when `imageai/` changes (or run it from the Actions tab: imageai → Run workflow). Its summary shows the tag to use, like `ghcr.io/khushm7/ebaymanager-imageai:sha-1a2b3c4`.
2. **Make the package public, once.** On GitHub: your profile → Packages → `ebaymanager-imageai` → Package settings → Change visibility → Public. Azure pulls it without credentials, and it contains no secrets.
3. **Once per subscription:** `az provider register --namespace Microsoft.App`.
4. **Sandbox:**
   ```powershell
   node scripts/make-keys.mjs                    # adds IMAGEAI_KEY to .dev.vars
   node scripts/azure-secrets.mjs sandbox        # uploads it to the Sandbox Key Vault
   $env:IMAGEAI_IMAGE='ghcr.io/khushm7/ebaymanager-imageai:sha-1a2b3c4'; node scripts/azure-infra.mjs sandbox
   node scripts/azure-deploy.mjs sandbox         # restarts the app so it reads IMAGEAI-URL
   ```
   Try each tool once in the editor on Sandbox. The first call takes up to a minute and a half.
5. **Production** (same, with the production vars file):
   ```powershell
   node scripts/make-keys.mjs .prod.vars
   $env:EBAY_CONFIRM_PRODUCTION='yes'; node scripts/azure-secrets.mjs production
   $env:IMAGEAI_IMAGE='ghcr.io/khushm7/ebaymanager-imageai:sha-1a2b3c4'; node scripts/azure-infra.mjs production
   node scripts/azure-deploy.mjs production; node scripts/check-production.mjs
   ```

**Later infrastructure updates:** set `IMAGEAI_IMAGE` again to keep or change the tag. Without it the photo AI
part is skipped, but nothing already deployed is removed. To update the models or code, change `imageai/`,
merge, and rerun step 4 or 5 with the new tag.

**To switch it off:** delete the container app and its environment in the portal, or never deploy them. The
editor then shows the AI tools as not set up, and everything else keeps working.

## Testing locally

```sh
docker build -t ebaymanager-imageai:local imageai
docker run --rm -p 8080:8080 --cpus 2 --memory 4g -e IMAGEAI_KEY=local-test-key ebaymanager-imageai:local
node imageai/test-local.mjs test/fixtures-photos/front.jpg    # results in imageai/out/
```

This was verified on 2026-11-13: all three tools returned correct results under these limits, with peak memory 1.8 GB.
